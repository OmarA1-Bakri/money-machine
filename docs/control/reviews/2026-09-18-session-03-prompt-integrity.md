## Findings

**H1 HIGH — JobStatus taxonomy contradicts the code.** The prompt (lines 13–24) declares eleven job states including `LEASED`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, `BLOCKED_EXTERNAL`, and `UNCERTAIN_EXTERNAL_EFFECT`. The canonical `JobStatus` enum in `src/money_machine/domain/enums.py:45-56` declares only nine states: `PENDING`, `BLOCKED`, `READY`, `RUNNING`, `SUCCEEDED`, `FAILED`, `TERMINAL_FAILURE`, `CANCELLED`, and `UNCERTAIN_EXTERNAL_EFFECT`. The prompt's `LEASED` and `BLOCKED_EXTERNAL` do not exist; `FAILED_RETRYABLE` and `FAILED_TERMINAL` do not match the code's `FAILED` and `TERMINAL_FAILURE`. D-0012 requires separate taxonomies for job state, retry class, and side-effect class; the prompt mixes them. Literal execution creates five enum values that tests, workflow configuration, and JOB_AND_EVENT_CONTRACTS.md do not recognize, breaking the taxonomy validator.

**H2 HIGH — successor/winner boundary is underspecified.** Action 8 (lines 117–139) lists event-to-successor mappings including `WINNER_DETECTED → CREATE_SUCCESSOR_SPEC` and `LISTING_CULLED → DEACTIVATE_LISTING`. The prompt does not state that `MULTIPLY` creates a distinct `workflow_id` (D-0017), that `require_successor_spawn` must be invoked to authorize cross-workflow entry at `DEDUPE_CHECK`, or that the parent workflow returns to `OBSERVING` while the successor begins its own lifecycle. D-0021's `SUCCESSOR_SPEC -> OBSERVING` edge and the Session 01 adversarial review finding 3 (D-0027 reference) require the orchestrator to call `require_successor_spawn` on the spawn path and reject same-workflow re-entry. Without this, an executor could implement inline successor creation that violates the workflow boundary and pulls a live winner back into `BUILDING`.

**H3 HIGH — receipt reconciliation contract is absent.** Action 4 (lines 57–75) requires retry classification and `UNCERTAIN_EXTERNAL_EFFECT` handling, and action 5 (lines 77–84) requires idempotency and "reconciliation before retry after timeouts." The prompt never defines how reconciliation reads effect state and provider state to resolve uncertain effects. `JOB_AND_EVENT_CONTRACTS.md:79-89` is the authority: reconciliation is an `EXTERNAL_READ` that queries the provider using the `idempotency_key` from `idempotency_records`, inserts a new `effect_attempts` row with updated `effect_state` (`CONFIRMED`/`ABSENT`/`UNKNOWN`) and incremented `reconciliation_attempt`, and moves the job to `SUCCEEDED`/`FAILED`/`BLOCKED` accordingly without repeating the mutation. Session 02 created three tables for this (D-0027, addendum point 2): `idempotency_records` (the reservation), `effect_attempts` (reconciliation tracking with `reconciliation_attempt` counter), and `receipts` (append-only committed effect records). The prompt must preserve this three-table structure rather than silently reinventing effect tracking, and reconciliation must never mutate the append-only `receipts` table.

**H4 HIGH — commissioning state vocabulary is incorrect, and Session 02 addendum conflicts with Session 03 scope.** Action 9's CLI command list (line 142–149) includes "run worker once" and "run scheduler once," and the exit criteria (line 187) say "Worker and scheduler survive restart." Session 02's addendum point 1 said "Job claiming is commissioned in Session 03," but Session 03's prompt contains no agent runtime, prompt loading, or evidence accumulation. ## Corrective addendum

This is the instruction set Session 03 executes. The prompt remains the unamended source of record.

1. **Use the canonical JobStatus taxonomy and map Action 4 failure classes to RetryClass + IncidentType.** The nine-state enum in `src/money_machine/domain/enums.py:45-56` is authority: `PENDING`, `BLOCKED`, `READY`, `RUNNING`, `SUCCEEDED`, `FAILED`, `TERMINAL_FAILURE`, `CANCELLED`, `UNCERTAIN_EXTERNAL_EFFECT`. Do not add `LEASED`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, or `BLOCKED_EXTERNAL`. Lease ownership is tracked in the `jobs` table's `worker_id`, `lease_start`, `lease_expiry`, and `heartbeat_at` columns, not as a job state. Retry eligibility is derived from `RetryClass`, `attempt`, `max_attempts`, and current `JobStatus`; it is not a state. External blocking (credential required, holder challenge) is represented by `BLOCKED` plus an incident of type `CREDENTIAL_FAILURE` or `PROVIDER_MISMATCH`; it is not a separate state. The prompt's Action 4 failure classes are not enum values; map them as follows: `RETRYABLE_TRANSIENT` → `FAILED` + evaluate retry per `RetryClass`; `AUTH_REQUIRED` → `BLOCKED` + `CREDENTIAL_FAILURE` incident; `REPAIR_REQUIRED` → appropriate `IncidentType` + repair job; `NON_RETRYABLE` → `TERMINAL_FAILURE`; `UNCERTAIN_EXTERNAL_EFFECT` → job state `UNCERTAIN_EXTERNAL_EFFECT` + reconciliation. Preserve Session 02's taxonomy tests that assert every contract value is admitted by its table.

2. **Implement the workflow boundary for MULTIPLY successors.** When `PortfolioDecisionJob` emits `WINNER_DETECTED` with a `PortfolioDecision(MULTIPLY)`, `SuccessorProductJob` creates a new `ProductSpec` with a distinct `workflow_id`, parent product/decision lineage, and `require_successor_spawn=True` per D-0017 and D-0021. The parent product's workflow transitions to `OBSERVING` and stays there; the parent never re-enters `DEDUPE_CHECK` or `BUILDING`. The successor workflow begins at `DEDUPE_CHECK` in its own `workflow_id`. `BuildSlotJob` invokes `require_successor_spawn(parent_workflow_id, successor_workflow_id, successor_spec_id)` before creating `DedupeJob`; that validator rejects a successor whose workflow equals the parent's. Test that same-workflow successors are refused, cross-workflow successors succeed, and the parent remains `OBSERVING`.

3. **Preserve and use the Session 02 effect-tracking tables.** Reconciliation of uncertain external effects reads the `idempotency_records` row by `idempotency_key`, queries the latest `effect_attempts` row for that key to get the current `reconciliation_attempt` count, performs an `EXTERNAL_READ` of the provider to determine current effect state, then inserts a new `effect_attempts` row with the resolved `effect_state` (`CONFIRMED`/`ABSENT`/`UNKNOWN`), incremented `reconciliation_attempt`, and the current timestamp. The worker reads the latest `effect_attempts` row to decide the job outcome: `CONFIRMED` moves the job to `SUCCEEDED` without retry, `ABSENT` moves to `FAILED` and evaluates retry policy, `UNKNOWN` increments the counter and moves to `BLOCKED` after the configured reconciliation budget is exhausted (opening an incident of type `UNCERTAIN_EXTERNAL_EFFECT`). The adapter's reconcile method is an `EXTERNAL_READ` that never repeats the mutation. Every external write: (a) reserves the `idempotency_key` in `idempotency_records` before the provider call, (b) inserts an `effect_attempts` row with the initial `effect_state` after the provider returns, and (c) inserts a `receipts` row with the committed effect details in the same transaction as the job result. `receipts` is append-only (enforced by trigger, D-0027) and is never updated; reconciliation state lives in `effect_attempts`. The three-table separation is: `idempotency_records` (reservation/deduplication), `effect_attempts` (mutable reconciliation tracking), `receipts` (immutable committed ledger). The prompt's action 5 "reconciliation before retry after timeouts" means: if a job reaches `UNCERTAIN_EXTERNAL_EFFECT`, reconcile by reading `effect_attempts`/`idempotency_records` and querying the provider before any retry.

4. **Preserve the fail-closed worker and scheduler boundary; supersede Session 02's "claiming is Session 03" with "claiming is Session 04."** Worker and scheduler continue to exit `EXIT_UNAVAILABLE = 78` as verified in Session 02 (D-0026 addendum 1, `IMPLEMENTATION_STATE.json` services entries). Implement database connectivity, migration status check, lease table existence check, configuration load, and agent registry initialization inside the worker/scheduler startup; log the result; then exit 78. No job is claimed, no lease is acquired, no state transition is applied, and Compose `restart: "no"` keeps the exit terminal. The CLI commands "run worker once" and "run scheduler once" remain fail-closed stubs that return exit 78. Session 02's addendum point 1 said "Job claiming is commissioned in Session 03," but Session 03's prompt has no agent runtime or commissioning plan, while the next prompt `07_SESSION_04_AGENT_RUNTIME_AND_ROSTER.md` is explicitly scoped to agent runtime. This addendum supersedes Session 02: commissioning evidence, agent promotion to `COMMISSIONED`, and removal of exit 78 are Session 04's scope. Session 03 builds the orchestration primitives (state machine, leasing, retries, reconciliation, successors, scheduler) with deterministic fake handlers but does not execute live agent work.

5. **Extend the existing workflow configuration, do not replace it.** `config/workflows.yaml` is the canonical workflow authority (D-0019, D-0022, D-0023). The scheduler reads that file to determine entry jobs (`ProvisioningCheckJob`, `ScheduleConfigurationJob`), job-to-successor mappings from `admitted_events` and `successor_job_types`, and schedule triggers from `ScheduleConfigurationJob`'s contract. Do not create a second Python/database workflow template registry. Workflow "templates" in the prompt's action 7 sense are type-safe job-creation helpers that consume the YAML configuration; they do not replace it. The scheduler's "create weekly-loop jobs" responsibility means: when `SCHEDULE_CONFIGURED` is emitted, create the first `WeeklyReviewJob` trigger per the configuration; when a weekly job completes, schedule the next week's instance. The same pattern applies to monthly and maturity timers.

6. **Five bounded slices with integration checkpoints.** Slice 1: job state machine, `PENDING->BLOCKED->READY->RUNNING` transitions, and tests with in-memory job rows. Slice 2: lease acquisition with `FOR UPDATE SKIP LOCKED`, worker claiming, heartbeat, expiry, graceful release, and concurrency tests proving two workers cannot claim the same job. Slice 3: retry policy (exponential backoff, max attempts, terminal vs retriable failure), idempotency reservation, receipt persistence, and uncertain-effect reconciliation. Slice 4: dependency resolution from event-to-successor map, transactional result+event+successor commit, and atomic rollback tests. Slice 5: scheduler (due-job promotion, weekly/monthly/maturity trigger creation, stalled-job detection), CLI commands (workflow/job inspection, manual retry), and required exit tests. Integrate and review after slices 2, 4, and 5.

7. **Event-driven successors from the canonical configuration; void the prompt's Action 8 example names.** `SuccessorFactory` reads `config/workflows.yaml`, maps each `admitted_events` entry to its job's `successor_job_types`, and creates at most the declared successors for that event. `DEDUPE_PASSED` creates `ProductBuildJob`; `DEDUPE_FAILED` creates `ReconceptProductJob`; `WINNER_DETECTED` (from `PortfolioDecisionJob`) creates `SuccessorProductJob`; and so on per the 45-job workflow. The prompt's Action 8 (lines 121–138) lists example event/job names (`CREATE_SUCCESSOR_SPEC`, `RUN_TEARDOWN`, `BUILD_NOTION_TEMPLATE`, etc.) that do not match the YAML job types; those examples are voided and replaced by the YAML authority. A result that emits an event not in the producing job's `admitted_events` is refused. A factory call with an event that has no successors creates nothing and returns success. Test that undeclared events are rejected, successor creation commits atomically with the parent result, and a uniqueness violation on `(workflow_id, job_type, parent_job_id)` rolls back the entire completion transaction.

8. **Deterministic tests with typed fake handlers.** Fake handlers accept `JobEnvelope`, return `AgentResult` with a typed output contract (e.g., `ProductSpec`, `DedupeResult`, `ListingPackage`), and emit the declared event synchronously. They use fixture `EffectReference` stubs with `effect_state=CONFIRMED` for external writes, or `effect_state=UNKNOWN` when testing reconciliation. Tests create throwaway PostgreSQL databases per `scripts/run_affected_tests.sh`, run real async transactions, and assert exact row counts, constraint rejections, and state transitions. The canonical `JobEnvelope`, `AgentResult`, and output-contract Pydantic models from Session 01 are used without modification. No test uses random UUIDs for job or workflow IDs; every ID is stable and derived from the test name or fixture data.

9. **Harden the exit criteria.** "Job linkage is functional" means: a test workflow of at least three dependent jobs (research → shortlist → qualification, or dedupe → build → QA) executes end-to-end with real handlers and database persistence, each successor is created transactionally with its parent's result, and the parent-to-child event linkage matches the configuration. "Successor creation is transactional" means: a test that raises an exception after result persistence but before successor creation proves the transaction rolls back and leaves no partial result, no event, and no successor. "Timers are durable" means: a test creates a weekly trigger, kills the scheduler, restarts it, and asserts the trigger survives and fires on schedule. "Tests cover concurrency and recovery" means: two workers race to claim the same ready job and exactly one succeeds; a worker with a live lease is killed mid-execution, its lease expires, and a second worker reclaims and completes the job; an uncertain-effect job is reconciled to `CONFIRMED` without retry, and a second uncertain job is reconciled to `ABSENT` and retried. Machine-earned receipts: test exit codes, database row counts, migration revision, constraint-rejection output, and `alembic check` result.
